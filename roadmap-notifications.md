# Telium Notification Federation Roadmap

This roadmap tracks the notification subsystem shared by Android, browsers, desktop, future iOS clients, homeservers, and remote guild servers.

The core rule is simple:

> **Push is a doorbell, not a message transport.**

The account homeserver is the single push authority for an account's devices. A remote guild server may decide that a member should be notified, but it never learns that member's FCM, UnifiedPush, or browser push endpoint. For remote guilds, notification preview data is encrypted to the destination device before it crosses federation, so the account homeserver can route and retain the notification without gaining access to remote-guild message plaintext.

The protocol design is documented in [`docs/notifications.md`](docs/notifications.md).

## P0 — Protocol foundation

- [x] Add per-device notification encryption keys, separate from MLS/message keys and push-provider keys.
- [x] Give each notification-capable device a revocable notification-only background credential.
- [x] Add a per-device notification inbox on the account homeserver.
- [x] Make inbox delivery idempotent by `(origin, source_id, device_id)`.
- [x] Add cursor-based pull and acknowledgement so dropped or duplicated push wakeups cannot lose notifications.
- [x] Add signed S2S notification-key discovery for remote guild servers.
- [x] Authorize key discovery only when the requesting server is the registered authority for a guild the local account belongs to.
- [x] Add signed S2S delivery of encrypted notification envelopes.
- [x] Reject notification envelopes from unrelated federation peers.
- [x] Keep the account homeserver blind to remote-guild notification plaintext.
- [x] Wake only the target device after its envelope is durably stored.
- [x] Reduce routine provider payloads to an opaque wake signal; providers must not be the source of truth.

## P0 — Guild notifications

- [x] Replace the current local-only guild mention wake path with notification federation.
- [x] Preserve mute/channel policy decisions on the guild authority before any notification is emitted.
- [x] Generate notification descriptors for explicit mentions and replies.
- [x] Add sane handling for `@everyone`/`@here` without turning federation into an amplification mechanism. `@here` stays realtime-only; `@everyone` reaches every eligible offline member through one durable paged job, bounded backpressure, and account-home federation batches rather than synchronous per-member requests.
- [x] Include enough encrypted routing metadata for a notification tap to open the correct guild/channel/message.
- [x] Do not copy remote-guild message plaintext into the account homeserver.
- [x] Retry failed S2S notification delivery with bounded backoff and idempotency.

## P0 — Direct messages and encrypted conversations

- [x] Add notification jobs for incoming DMs/group-chat frames. A frame whose sender set `notify` wakes every other local member of the conversation from that member's own account home, and a killed device is woken instead from the sealed `dm_hint` its own sender addressed to it.
- [x] Do not add a second MLS/decryption implementation just for notifications. Neither path looks inside the ciphertext: the account home decides from the sender's one-bit `notify` hint on the envelope, and the device decides from a fixed-shape envelope encrypted to its notification key.
- [x] For E2EE conversations, use a generic descriptor such as `Encrypted message` unless the normal client is already alive and can safely enrich it locally. The descriptor carries the sender's name and a constant body, and deliberately omits frame kind, length, epoch, and any count that would narrow the ciphertext.
- [x] Preserve sender/conversation privacy according to the user's notification-preview preference. The conversation descriptor goes through the same device-side redaction as every other kind, so `sender` mode shows the name over a generic body and `hidden` mode shows neither; the body is content-free in all three modes because there is nothing the server could have put there. Per-conversation mute is separate and lives at the account home, where the decision can be made before a device is woken at all: `PUT /_telium/v1/conversations/{id}/notifications`.
- [x] Ensure notification behavior survives sequencer re-anchoring and account migration. The wake is generated by each member's own account home from the frame it is already holding, so which server sequences the conversation never enters into it; the sealed hint is bound to the stable `dm:<conversation_id>` namespace rather than the current sequencer for the same reason. Migration follows the existing home-scoped rule, where registrations and queued inbox rows stay behind and the device re-registers with its new home.

## P0 — Android wake and fetch

- [x] Generate/store the notification private key in Android-controlled secure storage.
- [x] Register only the public notification key with the homeserver.
- [x] Store the notification-only fetch credential in Android secure storage, never in ordinary WebView-local application state.
- [x] Use Embedded FCM as the zero-configuration default where Google Play Services is available.
- [x] Support an external UnifiedPush distributor without changing the server protocol.
- [x] Keep a Google-free build possible by omitting Embedded FCM.
- [x] On wake, fetch the notification inbox from the account homeserver, decrypt descriptors locally, post native Android notifications, and acknowledge only successfully processed entries.
- [x] Do not require Telium itself to run an always-on foreground service for routine message notifications.
- [ ] Handle Android process death, Doze, token rotation, permission changes, and network recovery. The killed-process path and distributor re-registration now exist, and provider wakes queue a network-constrained WorkManager recovery drain before the immediate fetch so temporary offline/process-death failures survive for retry; this stays open until APK/device testing covers the full lifecycle matrix.

## P1 — Native notification UX

- [x] Android notification channels for messages, mentions, calls, and account/security events.
- [x] Notification taps route through the same canonical Telium message-navigation path as in-app navigation.
- [x] Conversation grouping and Android conversation metadata where useful. Rows are bucketed at the account home — per conversation, and per channel for a guild via a blinded hint the authority sends — so a reconnecting device is handed one notification per bucket with a count of what it stands for, rather than one per event. Android uses the bucket as the notification tag, renders message rows with `MessagingStyle` under stable opaque per-DM/per-channel group keys, and shows guild/channel context only in full-preview mode. Launcher/share shortcuts remain deliberately unpublished.
- [ ] Avatar/guild-icon enrichment without bypassing Telium media/privacy policy.
- [x] User preference for full preview / sender only / hide content.
- [ ] Optional inline reply only after its authentication and E2EE implications are understood.
- [ ] Optional bubbles for DMs after the basic pipeline is reliable.

## P1 — Calls and urgency

- [x] Treat incoming-call wakeups separately from routine messages. The authoritative conversation-call sequencer creates a dedicated short-lived `incoming_call` inbox descriptor only when a call transitions from zero participants to its first participant.
- [x] Use high-priority delivery only for genuinely time-sensitive incoming calls. Routine native/provider wakes use normal urgency; only the dedicated incoming-call doorbell uses high provider urgency, while the provider payload remains the same opaque wake.
- [ ] Integrate incoming call notifications with the Android call lifecycle work in `roadmap-android.md`. Native Answer/Decline actions hand Answer back to the authenticated voice client and keep Decline device-local. Authenticated calls now register with Core-Telecom where supported and use a credential-free CallStyle microphone foreground service whose system Hang Up action returns through the normal Telium voice-leave path. Pre-answer incoming-call Telecom registration and real-device background/lock-screen verification remain.
- [x] Expire stale call notifications quickly and never ring from an old queued wake. Android drops call descriptors without a usable timestamp or older than 60 seconds and auto-expires fresh call alerts at the end of that same window.

## P1 — Reliability and lifecycle

- [x] Notification inbox retention and bounded cleanup.
- [x] Dead-device/key cleanup when a device is revoked.
- [x] Push endpoint rotation without changing the notification key unnecessarily.
- [x] Notification-key rotation without invalidating unrelated account/device credentials.
- [x] Account migration carries notification state safely or forces explicit secure re-registration where carrying it would be unsafe.
- [x] Homeserver failover preserves pending notification inbox rows and resumes authoritative guild-side retry work only after promotion/demotion state is known.
- [x] Metrics/logging report delivery failures without logging message previews or ciphertext keys.

## P1 — Abuse resistance

- [x] Per-origin and per-user bounds on federated notification enqueueing.
- [x] Verify `(recipient, guild_server, guild_id)` against `remote_memberships` before key disclosure or envelope acceptance.
- [x] Refuse inactive/revoked device IDs.
- [x] Bound descriptor ciphertext size.
- [x] Reject duplicate `source_id` replays without generating duplicate notifications.
- [x] Ensure defederated peers cannot use notification endpoints as a side channel or spam relay.

## P2 — Cross-platform reuse

- [x] Let browsers consume the same homeserver notification inbox where that improves reliability without regressing normal Web Push UX. Capable browsers enroll a scoped P-256 notification identity, register their existing `PushSubscription` as `native-webpush`, and let the service worker drain/decrypt/validate the shared inbox; legacy `webpush` remains the fallback when enrollment or capability support is unavailable.
- [x] Reuse notification-federation semantics for a future iOS client while keeping APNs provider details device-side/account-home-side. The account home now speaks APNs directly with a provider JWT it signs itself, and sends the same content-free wake it sends everywhere else; a guild server still learns nothing about the device. No iOS client exists to receive it yet, and the alert an extension is expected to rewrite is described in `docs/notifications.md`.
- [x] Keep provider adapters below the Telium protocol boundary: FCM, UnifiedPush, Web Push, and future transports are replaceable delivery mechanisms.

## Completion criteria

The notification subsystem is considered complete when:

- [ ] a killed Android app can notify for a remote-guild mention; implementation exists, but this remains unchecked until an APK/device test proves it end-to-end.
- [x] the remote guild server never sees the device's push endpoint.
- [x] the account homeserver cannot read the remote-guild notification preview.
- [x] FCM/UnifiedPush can drop or duplicate wakeups without losing or duplicating authoritative notification jobs.
- [x] E2EE messages remain E2EE and do not acquire a notification-only decryption backdoor. Neither the guild-mention path nor the conversation path added one: the account home decides from the sender's `notify` bit and says `Encrypted message`, and the killed-app path uses separate per-device notification keys with fixed-shape opaque hints, so native Android never receives MLS decryption state.
- [x] device revocation also revokes background notification access.
- [x] an ordinary homeserver operator does not need a Firebase account, Google credential, or Telium-operated push gateway.
- [ ] an ordinary Android user with Play Services can install Telium, allow notifications, and do nothing else; implementation exists, pending APK/device verification.
