## Abuse resistance

- [x] **Harden every public-facing path against inexpensive abuse becoming expensive work.**
  - ~~Registration, authentication, friend and conversation requests, invites, mentions, uploads, federation and relay use all have budgets.~~ [`ratelimit.rs`](server/src/ratelimit.rs) keys them by token hash, bot application, federation socket or address, and `every_credential_check_in_the_tree_is_on_this_list` walks the source so that a new password-checking route cannot be added off the strict bucket by forgetting. Two of those budgets are not counted in requests at all: a bucket can be charged a variable number of tokens, all-or-nothing, so conversation creation pays per participant and `GET /guilds/{id}/search` — the widest read on the server, and the one path that used to ride the ordinary 200-burst read budget like any other GET — pays a price computed from how much of the guild the query actually has to touch. A one-character prefix over every channel costs a hundred times an exact term in one channel, because that is the ratio of the work, and a budget that charged them the same would not have fixed anything. `every_wide_read_in_the_tree_is_charged_by_what_it_costs` is the `every_credential_check` of that idea: it walks the source for the SQL shapes that sweep a guild and fails if one of them appears in a file that does not charge by cost, so the next wide read cannot be added off the cheap bucket by forgetting either. [docs/abuse-resistance.md](docs/abuse-resistance.md) documents the price list.
  - ~~Bound request bodies, connection counts, queues, fanout, decompression, parsing, and storage growth.~~ Bodies are capped globally and raised only for the routes that need it, a caller that announces a body and then stops sending is let go of while one that keeps sending slowly is not, gateway sockets are capped per account and per unidentified connection with a bounded outbox that disconnects rather than silently dropping events, and invites, pending friend requests and the federated media cache each have a ceiling with a per-origin share. Decompression is not bounded but absent — no request decoder is compiled in at all — and a test sends a body labelled `Content-Encoding: gzip` that is not gzipped and asserts it parses as literal bytes, so that wiring decompression in later breaks a test instead of quietly opening a zip bomb.
  - ~~Prevent a hostile federation peer from exhausting workers, sockets, memory, disk, or database capacity.~~ Signed bodies are read against a ceiling as they arrive instead of being buffered and then measured, remote media fetches and large bundle reads each run behind a semaphore with a per-sender exclusion so one peer cannot take every slot, and the connection pool is capped, so a federation flood cannot turn into unbounded database connections.
  - ~~Make operator-visible abuse telemetry useful without logging private message plaintext or cryptographic secrets.~~ [`telemetry_leaks.rs`](server/tests/telemetry_leaks.rs) does it twice over, because either mechanism alone would be evadable. A source walker masks comments and string bodies and then scans every logging macro, error context, `#[instrument]` and `Config` debug print for identifiers like `password`, `token`, `recovery` and `plaintext`, with exactly one reviewed exception. Then a live test boots a server, captures its output at TRACE, drives register, login, wrong password and a forged bearer with unique sentinel values, and asserts the sentinels appear neither in the log nor in the rendered metrics — and that no account-shaped value appears in a metric label at all, which is also what keeps scrape cardinality bounded.

  - ~~Metrics cover latency, error rates by class and by route, gateway connections and refusals, pool and database size, federation delivery failures, backlog depth *and* backlog age, backup freshness both local and offsite plus a stranded-key signal, standby lag, media and cold-storage bytes, and SFU region health.~~ `/metrics` is Prometheus exposition behind a scrape policy that is off by default and admits either an allow-listed socket address or a constant-time-compared token — never a forwarded header, deliberately not reusing the rate limiter's trusted-proxy list. ## Production installation and operation

- [x] **Provide a boring, supportable production deployment story.** — [docs/production.md](docs/production.md), [`preflight.rs`](server/src/preflight.rs), [deploy/](deploy/)

The nginx and Caddy examples exist to make the four settings that actually break a Telium install hard to miss — the WebSocket upgrade, a read timeout longer than the heartbeat, `X-Forwarded-For` matched by `rate_limit.trusted_proxies`, and a body limit — and the storage guidance puts data and backups on separate mounts, with the audit grading a `backup.dir` inside the data directory as a danger rather than a preference.

  - ~~Handle SIGTERM/graceful shutdown correctly.~~ In order: refuse new gateway upgrades, wake the sockets still waiting to identify, close the identified ones with 4005 so clients reconnect rather than sit out a timeout, settle briefly, then bound whatever HTTP work is left by `shutdown.grace_secs`. Past the deadline it logs the setting by name instead of hanging, and both supervisors are configured to wait longer than the server does, so nothing gets killed mid-drain by the thing that asked it to stop.
  - ~~Provide a production configuration validator and loud warnings for development-only or dangerous settings.~~ `telium-server check` runs exactly the audit that `serve` runs at start-up, and exits non-zero on anything graded a danger: a `server_name` with no dot in it, a loopback or plain-http public URL, a wildcard bind with no TLS in front, open registration with no administrator named, rate limiting switched off, backups written inside the data directory. `--strict` fails on warnings too. Every finding names the key and the remedy, because a test refuses to let one exist that does not.
  - ~~Support sane secret injection through files/environment without requiring an external secret manager.~~ `${env:NAME}` and `${file:/path}` are substituted into the parsed configuration before it is deserialized, whole-value only — `"prefix-${env:A}"` stays literal rather than half-expanding into something that looks like it worked — and an unresolvable reference is fatal at start-up and names the dotted key that used it. systemd `LoadCredential=` and Docker secrets both arrive through `${file:}` with nothing else installed. ## Updates and release delivery

- [x] **Build a trustworthy update story for every supported runtime.** — [docs/updates.md](docs/updates.md), [`updates.js`](web/src/lib/updates.js), [`updater.cjs`](web/electron/updater.cjs), [`sign-client-manifest.mjs`](scripts/sign-client-manifest.mjs)
  - ~~Give web, desktop, Android, and homeserver builds clear version/build identities.~~ Commit and build time are compiled into the server and defined into the web bundle, the Electron shell exposes its own installed version separately so a shell that has been updated and a bundle that has not can be told apart, and all of them report the same way. Android is the one that was actually broken: every APK shipped as `versionCode 1`, so no build could ever install over another. It is now minutes since a fixed epoch, derived from the commit's own timestamp rather than maintained by hand.
  - ~~Desktop and Android have version identity and no updater.~~ Every runtime now checks, and the question that decides the whole design is *who publishes the build a Telium user runs*. It is not their homeserver. Telium is self-hostable, so the server somebody chats on and the party that compiled their client are routinely different people with no relationship — and a client that asked its homeserver "is there a newer client, and where" would be handing every operator on the federation the ability to execute code on the machine of anyone who joined their guild. No confirmation dialogue converts "I decided to chat here" into "I decided to accept software from here", because the dialogue reads the same either way. So the update URL and the Ed25519 verification key are **compile-time inputs** (`VITE_TELIUM_UPDATE_URL`, `VITE_TELIUM_UPDATE_PUBLIC_KEY`) chosen by whoever built the binary, nothing reachable over the network can change them, and the homeserver is never asked. electron-updater and Tauri's updater plugin were rejected for the same reason plus coverage: they would have hidden the who-publishes question rather than answered it, and neither covers the browser tab, the distro package or the self-built binary — four of the five cases where the notice *is* the deliverable because nothing can be installed. [`updates.js`](web/src/lib/updates.js) is one implementation shared by every runtime; the Electron-specific part is only the last step, replacing the file.
  - ~~Nothing installs anything.~~ The AppImage now does, and only the AppImage: it is a single file replaceable by renaming another over it in the same directory, atomically, with no privilege the process does not already have. A `.deb` belongs to `dpkg`, a Play Store install to the store, and a self-built binary to whoever built it, so those get a sentence rather than a button — a control labelled "Update" that cannot update is precisely what teaches people the top of the screen is decoration. The renderer cannot influence any of it: the four IPC verbs take **no arguments at all**, because an `install(url, sha256)` bridge looks reasonable and is a remote code execution hole in the one process that loads content from homeservers. [`updater.cjs`](web/electron/updater.cjs) re-fetches, re-verifies against its own copy of the pinned key, re-selects the artifact and refuses any digest the publisher did not sign. The price is a second Ed25519 verifier — `@noble` in the renderer, `node:crypto` in the main process — paid deliberately and pinned by cross-implementation tests.
  - ~~Nobody is told they are running an old build.~~ A quiet, dismissible banner, never a modal: Telium holds a socket per guild, so the server that refused this build is one of several and the reader may be mid-conversation on the others, and a modal whose only button opens a web page is a hostage situation with a hyperlink. What a modal buys is that the reader saw it once; the banner buys that it **comes back** — dismissal is a snooze of three days, eight hours if a missed release was security-relevant, one hour if a server has refused the build, keyed to the situation so snoozing "0.3.0 is available" does not snooze tomorrow's security release. Close code 4015 is joined to it here, which is most of the user-visible value: "update the client" was a remedy nothing in the client could perform or explain, and now the connection banner keeps saying *which server* refused, in that server's own words, while the update banner offers the remedy. The security question is asked of every release the reader has missed rather than only the newest, so a reader four behind is told about the fix in the second of them and not about the tooltip in the fourth.
  - ~~Surface homeserver release/update information without silently installing arbitrary binaries.~~ `server/src/updates.rs` fetches the manifest on a schedule and does two things with it: log, and answer an administrator asking `GET /_telium/v1/admin/version`. The install is [`deploy/update.sh`](deploy/update.sh) on a timer, a person, or a configuration manager — never the server process. [docs/production.md](docs/production.md) states it as a boundary rather than a default: the server never installs anything, not a binary, not a migration, not a config change.
  - Signing is written on both sides and **switched off, because the key does not exist yet.** This is the one thing left and it is not a thing code can close. [`sign-release-manifest.mjs`](scripts/sign-release-manifest.mjs) signs the server manifest digest with Ed25519 over a fixed statement and `verify_manifest_signature` checks it; [`sign-client-manifest.mjs`](scripts/sign-client-manifest.mjs) does the same for the client manifest under a different statement prefix, so one key safely signs two documents and a signature lifted from one is not valid for the other. Both CI steps are gated behind `RELEASE_SIGNING_ENABLED`, the server's verification key defaults to empty and the clients' does too. Minting the seed, holding it as a secret an environment protects, publishing the public half and setting `TELIUM_UPDATE_URL` are human actions outside this repository — the same shape as the independent security review in P0 — and **the clients must then be rebuilt**, because the URL and key are compiled in rather than fetched. [docs/updates.md](docs/updates.md) is the six-step sequence.
  - ~~An updater that installs an unsigned artefact is worse than no updater.~~ A missing key is a named configuration state that disables updating, never a silent pass-through, and there are three of them rather than two: `configured`, `unkeyed` (one of the pair set — somebody's mistake, reported as one rather than softened into the third) and `unconfigured`. The rule is stronger than refusing to install: with no key the client **makes no request at all**. The guard sits at the top of `fetchManifest()` and of the desktop `check()`, not beside the signature check, because a version that fetched first and refused afterwards would hold an unverified document in a variable inside a function that returns documents, one careless early return from being believed. Both test suites assert it in that shape — a counting `fetch` whose count must be **zero** — since "downloaded it and then decided not to" is a different and much worse program that an assertion about the return value cannot distinguish. Verification is verify-before-parse and compare-the-statement-before-checking-the-signature, the second being the replay defence: an old signature document verifies perfectly against its own statement, so the statement is reconstructed locally and compared first. Both no-check states are named in words in the settings column, because a build silently never going to mention a security release is indistinguishable from a build that is up to date, and that ambiguity is how a fork ships for a year with a dead updater.
  - ~~Distinguish "update available" from "update required for compatibility/security".~~ Required is derived from two publisher-stated facts and never guessed: a `Security-relevant` trailer on the release, or a later release declaring a minimum protocol this build no longer satisfies. The client reads the server's verdict and does not infer its own, so the server stays the only thing that can make a notice urgent — and both halves have their own tests, including the case where both reasons apply at once.
  - ~~Show migration/config notes before risky homeserver upgrades.~~ `Breaking-change:` and `Upgrade-notes:` trailers are carried twice, into the manifest and onto the image as OCI labels, so [`deploy/update.sh`](deploy/update.sh) can read them off an image it has already pulled without asking the network anything. When it finds one it prints the notes and **stops**, leaving a marker behind, rather than going ahead on its timer — which is the only behaviour that makes writing the trailer worth the author's trouble.

## Mobile/federated notifications

- [x] **Complete federated notification aggregation for mobile clients.** — [`notifications.rs`](server/tests/notifications.rs), [`notification_federation.rs`](server/tests/notification_federation.rs), [`notification_push_auth.rs`](server/tests/notification_push_auth.rs), [`push.rs`](server/src/routes/push.rs), [`pushproviders.rs`](server/src/pushproviders.rs), [docs/notifications.md](docs/notifications.md), migration 0072
  - ~~Relay notification events from a guild authority to the user's account home instead of requiring the account home to already be in the guild traffic hot path.~~ Signed server-to-server posts to the account home, with batch forms so a busy channel does not become one request per recipient. The `notification_outbox` table is the part that matters: an account home that is down delays a wake instead of losing it, the queue is durable and backs off, and the worker that drains it is gated so a read-only standby never starts one.
  - ~~Aggregate/coalesce notifications at the account home and avoid duplicates across reconnects/devices.~~ The inbox is unique on origin, source and device and inserts ignore conflicts, so forty replays of one event across a reconnect produce one row and spend one budget. Coalescing happens twice, once in front of the doorbell and once in the inbox behind it. The doorbell half is a four-second per-device window, so twelve people replying to each other in a few seconds is one provider request per device instead of twelve; the leading edge always fires, which is the property worth protecting — the first message of a conversation is never delayed — and the window is held in memory on purpose, because a wake is already allowed to be lost and a restart that forgets the window errs towards sending one wake too many. The inbox half is migration 0072: a row carries a bucket, and inserting one tombstones the live rows in the same bucket for that device and carries their count forward, so the phone shows one line that says how many rather than a column of near-identical ones. It is a tombstone and not a delete, because deleting would free the uniqueness slot and let a federation retry ring the phone a second time for something already shown — exactly when the network is bad enough to be retrying. The bucket is a truncated domain-separated hash and never the identifier, and for a guild it is a hint the guild authority sends, mixed with the *authenticated* origin and the guild it was authorised for, so a peer can choose the granularity of its own buckets and cannot replay an observed hint to suppress somebody else's. A peer that sends no hint degrades to one bucket per guild. This mattered more than it looks: a superseded row is never handed to the device, so plain per-guild grouping would have let a mention in one channel *hide* a mention in another, and the channel is the one thing the account home must not learn.
  - ~~Add FCM and, when appropriate, APNs delivery.~~ Web Push with VAPID still covers every browser and any Android build that registers through a UnifiedPush distributor, so [`pushproviders.rs`](server/src/pushproviders.rs) exists only for the two cases where the device has a raw registration token and no endpoint to give: a build holding an FCM token from the Firebase SDK, and a native iOS app with an APNs device token. Both default to disabled, both refuse to boot when enabled without a readable credential rather than silently never delivering, and a server with neither configured rejects those registrations with a sentence naming the alternatives. Telium ships no Firebase or Apple credential and must not acquire one — they belong to whoever publishes the application. The file is deliberately small and its tests exist to keep it that way: what a provider carries is `{"type":"wake"}`, with no event id, guild, channel, sender or count, so there is nothing in it to leak and no second copy of the message format to maintain. That last claim is now asserted rather than asserted-about — the provider origins are configuration, so [`notification_push_auth.rs`](server/tests/notification_push_auth.rs) points both senders at loopback fakes and checks the exact bytes, the minted token, Apple's headers and ES256 JWT, and that `UNREGISTERED`, `410` and `BadDeviceToken` delete the registration while a `503` or a refused connection leaves it alone. The override refuses plaintext without the developer flag and preflight warns in production when one is set, because an origin override being honoured looks identical to one that is wrong.
  - ~~Register and revoke per-device push tokens safely.~~ Registration uses a narrow bearer that can reach the push endpoints and nothing else, so a token taken off a phone is not a session. Rotating a key discards only the old ciphertext, and revoking a device deletes its inbox rows in the same breath as the device itself — proved by a test that revokes and then asserts the notification access is gone immediately rather than at the next sweep.
  - ~~Do not expose E2EE DM plaintext merely to make a richer notification; use an "encrypted message" style fallback when content cannot safely be known.~~ `wake_conversation` now runs on the account home after a frame is delivered, and the descriptor it produces is a constant: the sender's display name, the literal body `Encrypted message`, and the conversation id. The server could not do better if it wanted to, which is the point of building it this way round. The single piece of judgement involved belongs to the sender, who sets `notify` on the frame to say "this is worth waking someone for"; it is one bit, it is relayed unchanged through the sequencer and across federation, and the server never reads it as a claim about content. `a_conversation_frame_notifies_the_recipient_without_revealing_anything` holds the guarantee, and `muting_and_an_unmarked_frame_both_produce_silence` holds the two ways a wake is correctly not sent.
  - ~~Define behavior across account migration, device revocation, and homeserver failover.~~ A move drops the old home's inbox, devices and subscriptions in one transaction; a revoked device loses its guild sessions at once; a queued job for a guild that has since moved is dropped rather than misdelivered to whoever holds the old address. The failover third no longer rests on the worker gate alone: [`notification_federation.rs`](server/tests/notification_federation.rs) stands up two real servers on loopback and sends a mention while the account home is down, then asserts it arrives when the home returns, that only the phone's key opens it, and that a replay never rings twice.

## Server administrator ownership and recovery

- [x] **Make server-administrator access survivable without making it dangerously easy to seize.** — [`ownership.rs`](server/src/ownership.rs), [`tests/ownership.rs`](server/tests/ownership.rs), [docs/server-ownership.md](docs/server-ownership.md), [docs/runbooks/lost-every-administrator.md](docs/runbooks/lost-every-administrator.md)

Granting refuses an account that could not sign in, because a roster reading "two administrators" when one of them is deactivated is the same mistake a row count makes.
  - ~~Nothing counts the usable administrators.~~ `USABLE_ADMIN` is a capability predicate, not a count of rows: an account is not a usable administrator if it is deactivated, scheduled for deletion, or holds the OPAQUE sentinel with no record beside it. The guard sits on all four ways an administrator can leave — revoke, deactivate, delete, and migrating the account to another server — and the refusal is coded `last_admin` with `user_id` and `attempted` as their own fields, so the person closing their account on an ordinary settings screen reads a translated sentence naming what they tried and what to do instead, rather than an English paragraph from a module called `ownership`. Dormancy deliberately decides nothing: it is reported loudly after ninety days and never refuses anything, because a hard rule treating a long-absent administrator as absent would hand the server to whoever noticed first.
  - ~~Require stronger authentication/reconfirmation for authority-changing operations.~~ `require_step_up` wants a fresh password check, recorded in its own table by migration 0059, inside a five-minute window that is deliberately not configurable — an operator cannot widen it to a working day. Fourteen destructive handlers sit behind it: suspension, purge, defederation, standby promotion, sunset. Spending it is graded on the strict login bucket, so guessing at it costs exactly what guessing at a login costs. The three routes that change *who the operators are* take the credential on the request itself instead of accepting that window, because a grant is not merely destructive — it is the operation that makes every destructive operation available to somebody else, permanently, and survives the revocation of the session that performed it.
  - ~~Administrator sessions and devices are visible only to their owner.~~ `GET /_telium/v1/admin/ownership/sessions` lists every administrator's devices and live session counts, and `DELETE .../sessions/{device_id}` ends one — device row deactivated, home sessions dropped, revocation announced to federation so guild servers stop honouring sessions minted from it. Two limits are deliberate: it touches administrators' devices only, so an ownership tool does not become a map of where every user signs in from; and it revokes the device, not the authority, so cutting off a lost phone is not also a demotion. It is announced to every administrator by name, including the one it was done to, because signing the other administrators out is move for move what an attacker does first, and an alert naming the actor is the difference between "flaky wifi" and a phone call. No last-administrator guard: a signed-out administrator can sign back in, the count never moves, and a guard would forbid the one case you most need — cutting off the last administrator when that administrator is the compromised one.
  - ~~There is no supported recovery for a sole administrator who has lost their credentials.~~ `telium-server admin recover <account>` opens a claim from a process that can open the database for writing, and grants the column to an account that already has its own front door: it mints no session, resets no password, and is structurally incapable of impersonation — the test reads the displaced account's credential columns and recovery address either side of a claim landing and asserts they are unchanged, and that neither account gained a session. It refuses before anything else if the database or its directory is writable by anybody but its owner, `authorized_keys`-style, and says which file, which mode and which `chmod` — not as a boundary against the caller, who can already run `sqlite3`, but because a claim opened on a group-writable file would record "the host's owner asked for this" when that is not what happened, and the refusal itself is audited. A server that still has an administrator who can sign in gets a 24-hour cancellable delay and an alert to everybody; one that has none gets the grant on the next tick, because a delay exists to give a legitimate administrator time to object and there is nobody to give it to.
  - ~~The audit log exists and is not the missing piece.~~ It now covers the authority changes too: `ownership.grant`, `ownership.revoke`, `ownership.revoke.refused`, `ownership.deny` for a failed credential on the way in, `ownership.session.revoke`, and the recovery family including `ownership.recovery.refused` for a claim turned away on permissions.
  - ~~[docs/runbooks/compromised-admin-account.md](docs/runbooks/compromised-admin-account.md) still says "there is no admin audit log".~~ Rewritten end to end against what the server actually does: the forensics open with `GET /_telium/v1/admin/audit`, every step is a supported route or subcommand rather than `sqlite3`, the two "what remains safe" claims that stopped being true — no grant through the API, no way to end anybody else's sessions — are replaced by what protects the server now instead of quietly deleted, and the new [lost-every-administrator.md](docs/runbooks/lost-every-administrator.md) covers the opposite emergency. The one gap left on that page is real and unchanged: nothing can require MFA of an administrator.

A copy of the database is no longer a copy of anybody's second factor; a copy of the database *and* the key file still is, which is why the key belongs somewhere the archives are not and both runbooks now start from that pair rather than from the database alone. The key rotates the way the backup key does — `mfa.previous_key_files`, mint, restart, `telium-server mfa rekey` — because the keyring exists precisely so a rotation is not a re-encrypt-everything outage; unlike the backup key the re-seal is a few hundred short rows, so there is no waiting period. Losing the key costs every enrolled account its authenticator, so a server with sealed rows and no key refuses to serve instead of booting into a lockout that each person discovers separately at their own worst moment — the one place in this document where availability loses to something else, argued out in [docs/secrets.md](docs/secrets.md#why-this-one-boot-failure-is-worth-it), and narrowed to the serving path so that the command that digs you out is not itself behind the refusal. Recovery codes are hashed separately and are *not* sealed under this key, which is what makes them the way back: a sign-in with an unopenable secret skips the TOTP check and still honours a code. Sealing writes to a new column rather than over `mfa_secret` (migration 0074), so a rollback to a build that predates this reads NULL and says "MFA enabled without a secret" instead of failing every code silently, and `telium-server mfa unseal --yes` puts the cleartext back for exactly that hour. Half of "cannot be rotated" *is* inherent — the other holder of a TOTP secret is a phone and no server reaches into it — but the server can stop honouring the old ones, and now does: `telium-server mfa reset-all` clears every enrolment, destroys every recovery code because a stolen database held those too, sets `mfa_reenrol_required` so `/mfa/status` can say *the protection you had was withdrawn* rather than silently not asking for a code, and mails every affected account with a verified recovery address. It prints how many had no verified address, because those people are told by nobody. What it cannot do is reach a connected client: it runs in a CLI process whose gateway hub has no connections, so a signed-in client finds out at its next `/mfa/status` — written down in [docs/secrets.md](docs/secrets.md#per-user-mfa-secrets) as a gap rather than glossed.

## Client recovery UX

- [x] **Make the client recover gracefully from common local and network failures.** — [`failure.js`](web/src/lib/failure.js), [`retry.js`](web/src/lib/retry.js), [`sendonce.rs`](server/src/sendonce.rs), [`recover.js`](web/src/lib/recover.js), [`diagnostics.js`](web/src/lib/diagnostics.js)
  - ~~Clearly distinguish account-home failure, guild-server failure, authentication failure, protocol incompatibility, and temporary reconnects.~~ One pure classifier, handed what the socket knew when it closed and returning a kind, an action and the sentence to show. Three rules do the work the close codes cannot: being offline pre-empts everything, because losing the network kills every socket in the same second with plausible-looking codes and classifying that per socket accuses five servers of failing at once; a 4015 renders the server's own words, because the side that knows which end is out of date composed a remedy before it read the token; and twenty seconds separates a blip from an outage, matching the moment failover gives up on the primary, so the client stops saying "reconnecting" exactly when it stops being true. The test that matters asserts the five cases produce five *different* instructions — a taxonomy whose branches all end in "try again later" has distinguished nothing.
  - ~~Preserve drafts and avoid losing user work during gateway reconnects.~~ The draft store is read from the local mirror before any server is reachable and merges per target rather than per row, so a gateway coming back hands over an account copy written before the outage without erasing the paragraph typed during it; the newer entry for each room wins and a cleared draft leaves a tombstone so the account's other devices clear it too. A send that fails puts the text and the attachments back in the composer rather than into the void, and says why in the reader's language rather than as `Failed to fetch`.
  - ~~Retry failed sends only when doing so cannot duplicate unsafe operations.~~ An allowlist, not a denylist, and every entry names the server-side mechanism that makes a second send indistinguishable from the first — an upsert, a `MAX()`, a delete by key — so an entry whose mechanism changes has to go. "Retry everything" posts messages twice and burns one-time prekeys; "retry nothing" means a dropped packet on a handover costs somebody their message. The line between them is drawn by a name: a channel send now carries a `nonce` minted before the first attempt, and the server keeps a five-minute claim on `(author, channel, nonce)` that answers the second copy with the message the first one wrote — never re-broadcasting it, never re-charging slow mode, and never running the new-member hold twice. The rule looks for the key itself rather than for a claim that one exists, so the retry cannot be opted into by asserting it is safe, only by doing the thing that makes it safe. A DM send is still never repeated: its nonce rides inside a frame encrypted to every device in the group, where the server that would have to match it cannot read it. So does a retry the person makes by hand, which is a new message with a new name, because the composer hands the text back precisely so it can be changed and a re-used key on edited text would answer with the original and lose the edit silently.
  - ~~Recover from stale/corrupt IndexedDB or local caches.~~ Self-healing rather than hand-holding: the snapshot carries a schema version and is validated field by field on read, a session blob that does not parse or does not have the right shape is cleared off the disk instead of being handed to a renderer, and a load that never reaches a screen is written into a boot-fault ledger that arms a cache wipe on the third attempt. The alternative — a "your local data may be corrupt, clear it?" prompt — loses, because the person who most needs it is looking at a blank page with no way to answer and the honest default for a cache is that it is disposable. An unreachable homeserver is deliberately not a corrupt disk: the ledger is cleared, not merely left alone, whenever a load reaches the outage screen, so an operator's bad afternoon never costs somebody their offline copy.
  - ~~Provide a safe "reset local client state" path and a diagnostics export suitable for bug reports without leaking secrets.~~ The reset is named for what it does — "reload everything from the server" — and its dialog says what goes and what stays, because a control that reads as "log out" while discarding undelivered drafts is a trap and one that reads as "delete my account" will not be pressed by the person who needs it. It drops exactly the two caches and carries the drafts across with their sync counters intact, along with the session, pinned identity keys and the device and MLS secrets, which are key material and not cache. The export is assembled field by field from an allowlist and never by filtering a snapshot of the store, since a filter is right until somebody adds a field and then fails silently and retroactively for every report already posted; values that could carry account content are reduced to counts, kinds, byte lengths and route shapes. The proof is the test rather than the code: a store and a disk seeded with a marker in every credential, identifier and piece of writing, and one assertion that the marker appears nowhere in either form the report is offered in, plus a pin on the set of sections so a new one cannot appear without somebody editing the line that lists them.
  - The idempotency registry is in process memory and forgets a key after five minutes. That covers every retry there is — a repeat arrives seconds after the attempt it repeats, and a restart closes the socket and forces a re-identify before anything can be sent again — but it is not durable and it is not shared. A deployment that ever runs two writer processes behind one address needs the persistent form instead: a nullable `nonce` column on `messages` and a partial unique index on `(channel_id, author_id, nonce)`. That is a migration and a write on the hottest path in the product, and it is deliberately not paid for until something makes the cheap version wrong.

What fails a run: the document or a pane needing sideways scrolling, text clipped by a box that never said it meant to clip, text drawn over other text, a control no scroller can bring back, a dialog taller than the window with nothing inside it to scroll, and — the anchor for the text mode — any readable element whose size does not move when the root font size does. The operator console had two, and both measured badly: a deleted report row at 0.72 put the account's full user id, the string an operator copies out to go look the account up, at 3.07:1 in light, and the absent-value em-dash at 0.6 reached 2.27:1 on the tinted tiles. # Maintenance rule

This file should stay **small enough to be scary**.

Do not copy every roadmap feature into it. Add something here when forgetting it could materially compromise security, privacy, recoverability, interoperability, accessibility, operator safety, or the credibility of a stable Telium release.

When a checkbox is genuinely complete end-to-end, mark it complete or move its historical implementation details somewhere more appropriate. Do not leave permanently half-complete checkboxes whose actual status cannot be determined.
